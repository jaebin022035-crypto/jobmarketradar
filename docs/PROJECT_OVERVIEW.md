# JobMarketRadar · 프로젝트 개요

> **채용시장 트렌드 분석 웹** — 공공데이터를 자동 수집·집계해 대시보드로 시각화하는 데이터 분석 서비스
> 폴리텍대학교 인공지능응용소프트웨어 수료 포트폴리오 · 2026-07-07 ~

## 0. 한 줄 소개

**"요즘 시장이 뭘 원하는지"** — 워크넷 채용공고 데이터를 매일 자동으로 모아, 직무·지역·경력·학력·고용형태 트렌드를 차트와 인사이트로 보여주는 대시보드입니다. 사용자가 데이터를 직접 올릴 필요 없이, **서버가 알아서 수집·적재·집계**합니다.

> 🌐 실제 서비스: `https://aisw-apps.kopoctc.kr/g/kopo13/JobMarketRader/`

## 1. 이 프로젝트를 통해 전달하고자 하는 메시지

이 프로젝트는 단순히 "동작하는 웹사이트"를 넘어, **데이터 엔지니어링과 백엔드·배포 역량을 처음부터 끝까지 직접 설계했음**을 보여주는 것이 핵심입니다.

### 💡 핵심 메시지
> **"원본 데이터를 그저 보여주는 게 아니라, 수집 → 적재 → 집계 → 시각화 → 자동 배포까지
> 전체 데이터 파이프라인을 내 손으로 구축했습니다."**

### 어필 포인트 (취업/포트폴리오 관점)

| # | 역량 | 이 프로젝트에서의 증명 |
|---|---|---|
| 1 | **공공데이터 API 연동 + 배치 자동 수집** | 워크넷(국민취업지원제도) API를 `node-cron`으로 매일 2회 자동 호출·업서트. 실패 재시도·수집 이력 관리까지 구현 |
| 2 | **데이터 집계/분석 설계** | 직종·지역·경력·학력·고용형태를 `GROUP BY`로 집계. 복잡한 로직이 아니라 **쿼리 설계**로 풀어냄 |
| 3 | **데이터 정합성·보안 의식** | SQL 인젝션 방지(파라미터 바인딩 전용), 업서트로 중복 방지, 수집 이력 기반 디버깅 체계 |
| 4 | **Git + Jenkins CI/CD** | `git push` → 빌드 → 테스트 → 배포 자동화 파이프라인 직접 설계 |
| 5 | **컨테이너화 설계** | Docker 멀티스테이지 빌드로 "어디서든 동일하게 실행" 가능한 산출물 보유 |
| 6 | **실사용 시각화 대시보드** | 다크테마·반응형·4종 차트·필터 연동·IT 직군 선별 등 정성 들여 마감 |
| 7 | **성장 과정 가시화** | 단계별(Step 1~6) 커밋 히스토리로 "어떻게 만들어졌는지"를 투명하게 기록 |

## 2. 시스템 아키텍처

```
[ 워크넷(국민취업지원제도) 채용정보 Open API ]
        │  (배치 수집 · 매일 2회 09:00/21:00, node-cron)
        ▼
[ collector.js ] ── API 호출(axies) → XML 파싱 → DB 업서트
        │
        ▼
[ SQLite DB (better-sqlite3) ] ── 4개 테이블 / WAL 모드
        │
        ▼
[ Express API 서버 (server.js) ] ── 정적 파일 + REST API + cron 동시 담당
        │  (GROUP BY 집계 쿼리 실행)
        ▼
[ 프론트 대시보드 ] ── Chart.js 시각화 + 필터 + 인사이트
        │
[ Jenkins CI/CD ] ── git push → Docker 빌드 → 테스트 → 배포 자동화
```

### 데이터 흐름 (5단계)
1. **수집** — `collector.js`가 cron 스케줄에 따라 목록 API → 상세 API 순회
2. **적재** — `emp_seqno`(고유키) 기준 upsert → 중복 없이 갱신/추가 (트랜잭션 보장)
3. **조회** — 브라우저가 Express에 집계 데이터 요청
4. **집계** — `GROUP BY` 기반 통계 산출 (직종/지역/경력/학력/고용형태/기간)
5. **시각화** — Chart.js로 4종 차트 + 자동 인사이트 텍스트 렌더링

## 3. 기술 스택 (실제 구현 기준)

### 3.1 백엔드 & 데이터

| 계층 | 기술 | 버전 | 역할 |
|---|---|---|---|
| **런타임** | Node.js | v20 | JS 단일 언어로 풀스택 구현 |
| **웹 프레임워크** | Express | ^4.19 | REST API + 정적 파일 서빙 + cron 호스트 |
| **데이터베이스** | SQLite | - | 파일 기반 DB (WAL 모드, 외래키 ON) |
| **DB 드라이버** | better-sqlite3 | ^11.3 | 동기 API, 파라미터 바인딩, 트랜잭션 |
| **HTTP 클라이언트** | axios | ^1.7 | 워크넷 API 호출 (재시도 로직 포함) |
| **XML 파서** | fast-xml-parser | ^4.5 | 워크넷 XML 응답 → 객체 변환 |
| **스케줄러** | node-cron | ^3.0.3 | 매일 2회 자동 수집 (`0 9,21 * * *`) |
| **환경변수** | dotenv | ^16.4 | API 키/포트/스케줄 관리 |

## 4. 데이터베이스 스키마 (4개 테이블)

```
job_postings          채용공고 헤더 (1공고 = 1행, emp_seqno PK)
   │ 1:N
   ▼
job_recruits          모집직무 (지역/경력/학력 집계의 주체)

collection_snapshots  수집 시점별 직종 집계 스냅샷 ("과거 vs 현재" 흐름 비교용)
collection_logs       배치 실행 이력 (운영/디버깅)
```

> **설계 철학:** 사용자 계정·게시물 CRUD가 없으므로 스키마는 단순하게.
> 복잡도는 스키마가 아니라 **"GROUP BY 집계 쿼리 설계"**에서 나옵니다.

## 7. 회고 · 배운 점

이 프로젝트를 통해 실무적으로 체득한 것들입니다.

1. **데이터는 API 응답 한 번 직접 때려보고 나서 설계해야 한다**
   문서만 보다 구현하면 필드명/구조가 달라 처음부터 다시 짜게 됩니다.
2. **복잡한 로직보다 쿼리 설계가 핵심**
   "직종별 통계"는 SQL 한 줄(`GROUP BY`)로 끝납니다. 스키마를 단순하게 잡고 집계를 쿼리에 맡기는 설계가 유지보수에 유리했습니다.
3. **회귀 버그는 server.log에서 가장 먼저 보인다**
   부분 수정 후 남은 잔재 변수(`ReferenceError`)가 연쇄 장애를 일으킨 사례 → "화면이 이상하다"면 로그부터 확인.
4. **배치는 "서버가 켜져 있어야 도는 것"**
   labport 환경 특성상 수동 수집이 사실상 주 갱신 수단이 됨 → 스케줄러 의존성의 한계를 체감.
5. **배포는 환경에 맞게 두 경로로**
   Docker 환경이 없으면 labport(Node 직접 실행 + Traefik)로 실배포하고, Docker 산출물은 "이식 가능성 증명"용으로 병행 보관하는 실용적 접근.

## 8. 한계 및 향후 개선점

| 항목 | 현재 한계 | 개선 방향 |
|---|---|---|
| **데이터 누적** | 마감 공고가 삭제되지 않아 DB가 계속 커짐 | `end_dt` 기준 만료 필터 / 주기적 정리 |
| **IT 직군 매칭** | 직종명 첫 값 + 키워드 매칭 → 약간의 노이즈 | `jobs_json` 전체 풀어 매칭 / 화이트리스트 전환 |
| **수집 자동성** | 서버 재기동 시 cron 스케줄 끊김 | 별도 워커 컨테이너 / systemd 영속화 |
| **관리자 보호** | `/api/admin/collect` 미인증 | 토큰 기반 보호로 외부 남용 방지 |
| **데이터 출처 한계** | 워크넷 등록 공고 기준 (전체 채용시장 아님) | 대시보드에 출처/한계 명시 중 |
