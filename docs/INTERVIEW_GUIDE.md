## 🎯 1분 자기소개 (엘리베이터 피치)

> 면접관: "이 프로젝트에 대해 설명해 보세요."

**"JobMarketRadar는 워크넷 채용공고 데이터를 매일 자동으로 수집해서, 직무·지역·경력·학력 트렌드를 대시보드로 보여주는 데이터 분석 웹입니다."**

제가 이 프로젝트에서 집중한 건 **'데이터를 단순히 화면에 뿌리는 게 아니라, 수집부터 저장·집계·시각화·배포까지 전체 파이프라인을 직접 설계했다'**는 점입니다.

Node.js와 Express로 백엔드를, SQLite로 데이터베이스를 구성했고, 워크넷 공공 API를 `node-cron`으로 매일 두 번 자동 호출해서 중복 없이 업서트하는 수집기를 만들었습니다. 수집한 데이터는 `GROUP BY` 집계 쿼리로 통계를 뽑고, Chart.js로 시각화했습니다. 여기에 Docker 멀티스테이지 빌드와 Jenkins 파이프라인까지 붙여서, `git push` 한 번이면 자동 배포되도록 CI/CD까지 직접 구축했습니다.

지금은 공고 **263건, 모집직무 368건**을 운영 중이고, **"IT·개발 직군만 보기" 토글**처럼 실사용 관점의 기능까지 넣은 상태입니다.

## 💡 왜 이 프로젝트를 만들었나 (문제의식)

> 면접관: "이 프로젝트를 왜 만들게 됐죠?"

취업 준비를 하면서 느낀 건, **"요즘 어떤 직무·기술을 많이 뽑는지"를 개인이 감으로만 파악하고 있었다**는 점입니다. 공고를 일일이 뒤져야 하고, 그마저도 개별 공고지 '시장의 흐름'은 보이지 않더라고요.

그래서 공공 데이터를 자동으로 모아서 **통계와 추세**로 보여주면, "지금 시장이 뭘 원하는지"를 한눈에 볼 수 있겠다고 생각했습니다. 핵심은 원본(공고)이 아니라 **집계된 인사이트**를 제공하는 거고, 이게 일반적인 구인 구직 사이트와의 차이점입니다.

## 🛠 기술 스택 선택 이유 (왜 이 기술인가)

> 면접에서 가장 자주 나오는 "왜 이 기술을 썼나요?"에 대한 답입니다.

### 백엔드 — Node.js + Express
**"데이터를 하나의 언어(JS)로 수집부터 API까지 통일하면, 1.5주라는 짧은 기간에 무리 없이 완성할 수 있기 때문입니다."** 프론트도 바닐라 JS로 짜서, 문맥 전환 없이 풀스택을 커버할 수 있었습니다.

### 데이터베이스 — SQLite (better-sqlite3)
**"파일 기반이라 별도 설치나 서버가 필요 없고, 단일 인스턴스에서 수집기 1개 + API 서버 1개가 도는 구조라 동시성 부담이 적어서 선택했습니다."** better-sqlite3는 동기 API라 코드가 단순하고, `ON CONFLICT` 업서트와 트랜잭션을 안정적으로 지원합니다. 데이터가 커지면 PostgreSQL로 마이그레이션하는 확장 포인트로 남겨뒀습니다.

### 수집 — node-cron + axios + fast-xml-parser
**"워크넷이 XML로 응답해서 fast-xml-parser로 파싱했고, axios는 재시도 로직을 넣기 좋아서 선택했습니다."** cron은 매일 09:00·21:00 두 번 실행(`0 9,21 * * *`)하고, API 호출 사이 200ms 대기로 호출 제한을 지켰습니다.

### 시각화 — Chart.js (CDN)
**"별도 빌드 없이 CDN 한 줄로 끝나고, 다크테마 커스터마이징이 자유로워서입니다."** 4종 차트(직종/지역/경력/학력)를 그렸습니다.

### 배포 — Docker(멀티스테이지) + Jenkins
**"'어디서든 동일하게 실행된다'는 것과 '배포 자동화'를 모두 증명하고 싶었습니다."** 멀티스테이지로 빌드 단계에서 better-sqlite3 네이티브 컴파일(python3/make/g++)을 처리하고, 런타임엔 빌드 도구를 빼서 이미지를 가볍게 했습니다. SQLite 파일은 볼륨(`./data:/app/data`)으로 영속화했습니다.

## 🏗 아키텍처 & 내가 구현한 핵심

```
워크넷 API → collector.js(수집) → SQLite(업서트) → Express(GROUP BY 집계) → Chart.js(시각화)
                                                              ↑
                                              Jenkins: git push → 빌드 → 테스트 → 배포
```

**내가 직접 설계·구현한 핵심:**

1. **수집 파이프라인** — 목록 API(페이지네이션 100건씩 순회) → 상세 API → 트랜잭션 기반 업서트. `withRetry`로 실패 시 2회 재시도, `collection_logs` 테이블로 실행 이력 관리.
2. **집계 API** — 직종·지역·경력·학력·고용형태를 `GROUP BY`로 통계 산출. 복잡한 애플리케이션 로직 대신 **쿼리 설계**로 풂.
3. **공통 필터 빌더** — `buildFilters(query)` 헬퍼 하나로 모든 트렌드 API의 WHERE 절을 재사용. **파라미터 바인딩만 써서 SQL 인젝션 원천 차단.**
4. **IT 직군 선별** — 키워드 매칭으로 82개 직종 중 개발자 맥맥락의 12종/30건만 필터링하는 토글.
5. **CI/CD** — Dockerfile/compose/Jenkinsfile을 실제 코드 정합성(DB 경로·포트·env)과 일치시켜 작성.

## 🧗 가장 어려웠던 점 & 해결 (STAR — 면접 하이라이트)

> 이 부분이 면접에서 **가장 기억에 남는 질문**으로 이어집니다.

### 사례 1: 회귀 버그로 인한 연쇄 장애 (가장 인상 깊은 경험)

**상황(Situation):** 필터 연동 기능을 전면화(Step 5.5)하면서 "지역 하위 분포와 직종 선택란이 사라졌다"는 피드백이 왔습니다. 차트는 안 그려지고, 드롭다운도 비어 있었습니다.

**과제(Task):** 멀쩡하던 기능이 고장난 회귀 버그의 원인을 찾아 빠르게 복구해야 했습니다.

**행동(Action):** 먼저 **브라우저가 아니라 `server.log`부터 봤습니다.** 화면이 이상할 때 가장 빠른 단서가 서버 로그라는 걸 경험적으로 알고 있었거든요. 거기에 `ReferenceError: drilldown is not defined`가 반복되고 있었습니다. 원인을 추적하니, 부분 수정하면서 선언부(`let drilldown`)는 지웠는데 `else` 블록 안의 할당문(`drilldown = false`) **잔재 1줄**을 남긴 것이었습니다. Node strict mode에서 정의되지 않은 변수에 할당하니 런트 에러가 났고, 이게 region API 실패 → 프론트 `fillFilterOptions` 중단 → 드롭다운/차트가 모두 비어버리는 **연쇄 장애**로 번진 거죠. 잔재 1줄을 제거하니 해결됐습니다.

**결과(Result):** `/api/trends/region?period=all`이 정상적으로 26건을 반환했고, 화면이 모두 복구됐습니다.

**배운 점:** 부분 수정 시에는 함수 전체를 다시 읽어 잔재를 확인해야 한다는 것, 그리고 "화면이 이상하다면 `node --check`(문법 검사)만으로는 잡히지 않으니 **서버 로그를 먼저 보는 습관**을 확실히 들였습니다.

### 사례 2: 집계 로직 설계 — 어디서 연산할 것인가

처음엔 "경력 분포" 같은 걸 애플리케이션 코드에서 버킷팅하려다가, **데이터가 많아지면 서버 메모리와 응답 속도에 부담**이 된다는 걸 깨달았습니다. 그래서 가능한 모든 집계를 **SQL `GROUP BY`로 밀어 넣고**, 복합값("경력|신입") 정규화 같은 것만 JS 헬퍼(`careerBucket`)로 처리했습니다. 이 설계 덕분에 직종별 통계가 SQL 한 줄로 끝났고, 정합성 검증도 DB 직접 카운트와 비교해서 쉽게 할 수 있었습니다.

## ❓ 예상 면접 질문 & 모범 답안

### Q1. "이 프로젝트에서 본인의 역할은?"
단독 개발입니다. 설계(API 명세, DB 스키마), 구현(수집기, API, 프론트), 배포(Docker, Jenkins) 전 과정을 혼자 했습니다. 단계별로 Step 1~6으로 나눠 커밋 히스토리를 남겨서, 어떻게 만들어졌는지 투명하게 볼 수 있습니다.

### Q2. "왜 업서트(upsert)를 썼나요?"
워크넷 API가 마감일이 바뀌거나 정보가 갱신된 동일 공고를 다시 줍니다. 일반 `INSERT`를 쓰면 매일 수집마다 중복 에러가 나고, `emp_seqno`(고유키)를 PK로 잡고 `ON CONFLICT(emp_seqno) DO UPDATE`를 쓰면 **이미 있으면 갱신, 없으면 추가**가 한 번에 처리됩니다. 공고 헤더와 모집직무(1:N)는 트랜잭션으로 묶어 원자성을 보장했습니다.

### Q3. "SQL 인젝션은 어떻게 막았나요?"
**파라미터 바인딩(`?`)만 사용하고, 절대 문자열 결합으로 쿼리를 조립하지 않았습니다.** 모든 트렌드 API의 WHERE 절은 `buildFilters` 헬퍼 하나에서 조건 배열과 파라미터 배열을 반환하는 구조로 통일했기 때문에, 새 API가 생겨도 동일한 안전한 패턴을 재사용합니다.

### Q4. "배치 수집이 실패하면 어떻게 되나요?"
`withRetry`로 최대 2회 재시도하고, 성공/실패 여부를 `collection_logs` 테이블에 `status`(success/fail)와 함께 기록합니다. 그래서 수집이 안 됐으면 로그 테이블부터 확인하면 원인을 바로 알 수 있습니다. 또 `/api/admin/collect` 엔드포인트로 수동 트리거도 가능합니다.

### Q5. "배포 환경에 Docker가 없으면 어떻게 했나요?"
실제 labport 환경엔 Docker가 없어서 두 경로로 풀었습니다. **실배포는 Node 직접 실행 + Traefik 자동 외부 공개**로 처리하고, **Docker 산출물(Dockerfile/compose/Jenkinsfile)은 "어디서든 동일하게 실행된다"를 증명하는 이식성 자료로 작성**했습니다. 산출물은 실제 코드의 DB 경로·포트·env 변수와 정합성을 맞춰뒀기 때문에, Docker 환경으로 가져가면 바로 동작합니다.

### Q6. "가장 아쉬운 점이나 개선하고 싶은 점은?"
세 가지가 있습니다. 첫째, 마감 공고가 삭제되지 않아 DB가 계속 커지는데, `end_dt` 기준 만료 필터를 넣으면 좋겠습니다. 둘째, IT 직군 매칭이 직종명 첫 값 + 키워드라 약간의 노이즈가 있는데, `jobs_json` 전체를 풀어 매칭하면 정확도가 올라갑니다. 셋째, cron이 서버 프로세스 안에서 돌아서 재기동 시 스케줄이 끊기는데, 별도 워커 컨테이너로 분리하면 해결됩니다. **이런 한계를 인지하고 해결 방향까지 잡아둔 게 저의 강점이라고 생각합니다.**

### Q7. "팀으로 일할 때 어떤 개발자인가요?"
단계별로 쪼개서 커밋하고, 문서(계획서, 워크로그)를 꼼꼼히 남기는 스타일입니다. 회귀 버그를 겪은 뒤로는 부분 수정 시 함수 전체를 다시 읽고, 작업 과정을 `step5.5-worklog.md`처럼 기록에 남겨서 동료가 맥락을 이해할 수 있게 합니다.

### Q8. "크롤링 말고 왜 공공 API를 썼나요?"
합법성과 안정성 때문입니다. 크롤링은 사이트 구조가 바뀌면 깨지고, 호출 제한·법적 리스크가 있습니다. 워크넷은 공식 Open API를 제공해서, **인증키 기반으로 안정적으로 데이터를 받을 수 있고 출처도 명확**합니다. 단, 이 데이터는 '워크넷 등록 공고 기준'이라는 한계를 대시보드에 명시해 과대 해석을 막았습니다.
